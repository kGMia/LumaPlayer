硬件加速器（Neural Accelerator）利用度解构与深度优化建议

FSRCNNX 8 / 16 完全未利用 (0%)

当前硬件调度机理：
目前以普通 GLSL Fragment Shader 挂钩在 mpv GPU 栅格化管线执行。完全依赖通用 GPU ALU 核心执行像素着色，根本无法调用 M5 芯片的 GPU Neural Accelerator（张量计算单元）或 ANE（神经引擎）。FSRCNNX 16 包含 30 多个着色器阶段，导致大量的全屏中间纹理（FBO）往返读写，显存带宽开销巨大。

工程优化路径：

  • Metal / MPSGraph 原生移植：将预训练的卷积核参数、PReLU 激活与 PixelShuffle 上采样重构为 MPSGraph 图，启用 FP16 精度，直接调用 M5 专有张量运算指令。预期可降低 45%~60% 的推理耗时。
  • 编译导出至 Core ML (针对 ANE)：将模型转换为 .mlmodelc 并指定执行单元为 all 或 neuralEngineOnly。将超分工作完全从 GPU 卸载至 Apple Neural Engine，实现 GPU 零渲染负担。
  • 计算着色器（Metal Compute Kernel）贴图融合：利用 Metal 的 Threadgroup Memory 缓存分块特征，消除十余次纹理内存往返读写（Memory Roundtrip）。

Apple VideoToolbox (SR & FI) 高度硬件加速 (系统黑盒)

当前硬件调度机理：
直接调用系统 VTFrameProcessor，其底层是 macOS 私有深度硬件加速管线。系统按输入分辨率自动分发至 ANE、GPU 加速器或专用媒体引擎（Media Engine）。这也是其单帧耗时极低（4.7ms / 5.8ms）的核心原因。

工程优化与局限：

  • 应用层模型黑盒：模型拓扑与权重不可修改，且目前在 M5 上 Apple SR 不支持 1080p→4K，画质调优手段仅限于前后后处理。
  • 已实施的零拷贝优化：本项目已在 AppleBackend.m 中构建了复用的 CVPixelBufferPool，直传 NV12 格式，消除了无谓的 RGBA 中间拷贝。
  • 后续建议：保持当前管线，用于笔记本电池供电模式下的低功耗超分与平滑插帧。

RIFE Metal v4.26 部分利用 (GPU 张量已用 / 存在内存搬运瓶颈)

当前硬件调度机理：
已采用 FP16 半精度张量、MPSGraph 编译图（Level-1 优化），并在 Xcode 27 上默认启用了 M5 自动卷积布局（Auto Layout）。卷积阶段已充分调用 GPU 张量单元。但仍存在瓶颈：mpv 到 C ABI 的软件解码/swscale 格式转换仍在 CPU 端进行。

工程优化路径：

  • 端到端 Zero-Copy Pipeline：打通 libmpv 硬件解码（hwdec=videotoolbox）输出的 CVPixelBuffer 直接绑定到 MPSGraph 输入张量，彻底移除 CPU swscale 与内存拷贝。
  • 边界 Padding / Crop 移至 GPU：将目前在 Swift 流管线中为对齐 32 像素所做的 CPU 边界填充与裁剪，改由 Metal Compute Shader 执行。
  • Metal System Trace 指令重叠：通过 Xcode 捕获跟踪分析，将光流扭曲（Warping/Blend）与下一帧的特征编码阶段（Feature Encoder）做计算流水线重叠。
