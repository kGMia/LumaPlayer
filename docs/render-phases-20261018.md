# 渲染尖峰诊断与亮度采样优化

## 背景

用户最新的约 183 秒记录中，原位换档没有新增丢帧；其后有三处累计增加 9 次丢帧，其中两处伴随约 88ms、101ms 的 mpv 绘制调用峰值。现有数据不能区分驱动提交、内部资源等待或其他调度影响，不能将其直接归因于亮度采样。

## 已改动

- 无待回收亮度数据时，不再查询 OpenGL 的 pixel-pack 状态。
- 未到两秒采样间隔时，不再查询 OpenGL 状态。
- 亮度采样开关值未变化时，不重复请求 redraw。
- 原先用于暂停时回收数据的延迟回调，现在仅在存在待回收 PBO 时获取上下文并尝试回收，不再进入 mpv update/render/report-swap 流程。已有普通帧仍可回收数据；GPU fence 检查继续采用零超时。
- 增加八项 CPU 墙钟耗时：make-current、CGL 锁等待、mpv update、mpv render、亮度回收、亮度采样提交、buffer swap、report-swap。独立的亮度回收定时器另记 P95/max。

mpv 的 `BLOCK_FOR_TARGET_TIME` 原本已经设为 0，本轮保持不变。`draw` 仍是完整 mpv render 调用耗时；尚未将其内部 GPU/驱动等待进一步分解，也没有将 CPU 调用耗时伪称为 GPU 执行耗时。

## 慢帧记录

任一调用达到 20ms，或相邻成功提交间隔达到 50ms，记录该帧的单调时钟时间、序号、各项耗时、是否显式重绘及是否由 mpv 帧更新触发。

原生侧只保留最近 16 项，播放器快照仅导出上次快照之后的新事件；未及时读取导致的覆盖数单独报告。暂停、定位、窗口遮挡也可能产生长提交间隔，因此“慢事件”不是新增的丢帧计数。

`pipeline_profile.py --summarize-player` 增加 `render_slow_events`：去重后保留最大的 32 项并按时间排列，列出耗时最大的调用，不把相关性当作根因。旧日志没有这些字段时返回空事件列表。无需开启逐帧控制台输出。
