# RIFE 原位换档与卡顿诊断（2026-10-17）

## 本轮改动

此前 balanced → fast 会重建整条视频滤镜链并精确定位到当前位置。本轮为仅改变 RIFE 档位的操作加入 `vf-command` 路径：在原滤镜工作线程的帧对边界替换模型，保留时间轴、上一源帧和待输出帧；不暂停、不重置滤镜、不主动 seek。

只有滤镜数量、其他参数和 Shader 均不变，且没有正在进行的预热时才使用此路径。目标 FPS、滤镜顺序、其他增强参数发生变化，或后端不支持命令时，仍使用原有重建流程。模型初始化失败会旁路回原始播放，并通过 `error-bypass` 明确报告；档位字段必须结合运行状态解读。

新模型仍需初始化与播种，换档不等于零耗时；构建时新旧模型会短暂共存。初始化耗时单独记录为 `tier_switch_ms`，不混入稳态推理窗口。没有增加长期驻留的第二模型缓存。

## 诊断

- 滤镜元数据：`tier_switch_pending`、`tier_switches`、`tier_switch_ms`。
- 播放器计数：`iive-rife-tier-commands`、`iive-filter-rebuild-seeks`，用于区分原位换档与重建定位。
- 渲染信息：OpenGL 上下文锁等待 P95、绘制/交换/锁等待最大耗时、最近和最大提交间隔。

最大值从渲染统计重置时累计。提交间隔也包含暂停、定位、遮挡等正常情况，不能单独认定为卡顿或真实显示帧率。没有添加 GPU 图像读回。

报告工具用原生滤镜元数据判断实际所选档位，并保留 `initial_tier`，避免 mpv 的滤镜创建参数仍是 balanced 时误报。原始日志不改写。

## 已做的基础验证

- Debug 播放器及依赖构建通过。
- Objective-C 换档条件检查通过：只接受孤立的合法档位变化，拒绝 FPS、其他参数、滤镜数量、重复档位等变化。
- 无窗口 mpv 合成输入检查通过：256×128、24fps、1 秒输入，balanced → fast 后仍输出连续的 60 帧；时间戳为 `i/60`，滤镜 generation 未变，有真实合成帧，正常 EOF，无旁路。
- 此小尺寸样本记录换档初始化约 73.536ms；不是 1080p 测量，也不是视觉流畅度结论。
- Metal 定向测试通过：48fps 与 60fps 换档后时间轴、合成帧与末尾输出保持正确。
- 报告工具 6 项单元检查通过。

结果位于 `benchmarks/results/live-tier-*20261017*`。未进行完整回归或 GUI 验证。

## 用户验证与后续方向

使用同一 1080p24 视频和自动保护，从 balanced 播放至自动降为 fast，重点观察是否仍有明显停顿或跳回，并导出窗口诊断。换档命令计数应增加，原位换档本身不应增加滤镜重建定位计数。

下一步先依据新增诊断区分偶发停顿来自推理、OpenGL 锁等待还是提交节奏，再决定是否预热 fast 模型或优化呈现调度。若引入预热，需限制 GPU 竞争和临时内存峰值；不能以持续保留双模型换取未经测量的收益。其他方向可继续检查纹理池回收与长期播放内存趋势。EDR 继续搁置。
