# OneDrive preview — 2026-10-21

## What is implemented

Settings → Network now includes **OneDrive · Preview**: public client ID configuration, Microsoft sign-in, local disconnect and a SwiftUI file browser. File → Open Network → OneDrive opens the same browser. The browser supports folders, back navigation, refresh, paginated loading, playback and queue append. The existing same-folder switch includes ordinary supported media from all pages, up to 5,000 media entries / 100 pages. Hidden entries and subfolders are excluded from auto-enqueue.

Both WebDAV and OneDrive now use `RemoteMediaOrigin` and the existing `on_load` queue hook. OneDrive entries retain drive/item/account identity; temporary CDN URLs are resolved at playback start. No Graph access token is sent to mpv or to a content/thumbnail URL. Existing RIFE/SR processing and performance guards remain after decoding. This reuse is implemented, but real OneDrive playback and enhancement have not yet been tested with an account.

Queue metadata uses Graph's duration, size and thumbnail APIs instead of decoding cloud video for covers. The existing bounded, coalesced remote metadata cache is shared by the two provider paths. Graph JSON reads are capped at 6 MiB and image reads at 1 MiB. Authenticated API requests accept only HTTPS `graph.microsoft.com/v1.0/`, refuse redirects and validate pagination URLs. A 401 triggers one silent refresh retry; 429/503 get one short retry. Longer outages remain visible errors, without an unbounded retry loop.

## Registration and cost clarification

Microsoft Entra ID has a [Free tier](https://learn.microsoft.com/en-us/entra/fundamentals/licensing), separate from P1/P2/Suite. However, access to an app-registration tenant is a prerequisite. Microsoft's [tenant creation documentation](https://learn.microsoft.com/en-us/entra/fundamentals/create-new-tenant) restricts creating additional workforce tenants from the admin center to paid customers and points users without an eligible tenant to Azure free-account signup. Thus a personal Outlook/OneDrive account alone does not guarantee immediate app-registration access; signup or tenant permissions may be an obstacle. Do not buy P1/P2 solely to test this preview.

The current configurable client ID is a developer-preview setup. A finished public player should use its publisher's registered public client ID so ordinary users only sign in. This project does not currently have that registration. OneDrive can remain unused while local playback and WebDAV continue working.

## Register your application

1. Open **Microsoft Entra admin center → App registrations → New registration**. Create an application such as “IIVE Player Personal”. Choose a supported-account option that includes personal Microsoft accounts; use an organizational option only if that is your intended account. Registration requires access to an Entra directory with permission to register apps. If your account lacks this access, this must be resolved in Microsoft Entra first; the player cannot create that permission.
2. Under **Authentication → Add a platform → iOS / macOS**, use bundle ID `org.iina-community.video-enhancer.player`. Verify that the registered redirect URI is exactly:

   `msauth.org.iina-community.video-enhancer.player://auth`

3. Under **API permissions**, add Microsoft Graph **Delegated permissions → Files.Read**. No application-wide permission or write scope is needed for this implementation. Organizational policy may require administrator consent.
4. Copy **Application (client) ID** from Overview. Do not create or enter a client secret. The player is a public native client, and MSAL handles the authorization-code/PKCE exchange.
5. Open IIVE Player → Settings → Network, paste the public ID, choose **Save Client ID**, then **Sign In…**. Authentication uses Microsoft's web page through the system authentication session. Choose **Browse…** after successful login.

These steps follow Microsoft's [macOS MSAL configuration guide](https://learn.microsoft.com/en-us/entra/msal/objc/install-and-configure-msal), [authorization-code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), and the [directory API's delegated permissions](https://learn.microsoft.com/en-us/graph/api/driveitem-list-children?view=graph-rest-1.0). Portal wording can vary by account and tenant policy. No application was registered, and no account was accessed during development.

## Authentication and dependency details

MSAL **2.16.0** is an exact Xcode Swift Package dependency, with revision pinned in `IIVEPlayer.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`. Its official binary checksum was verified. `MSAL-LICENSE` contains its MIT notice and is copied into application Resources.

The integration reads the SDK's actual `MSALPublicClientApplication`, `MSALWebviewParameters` and `MSALCacheConfig` APIs. Private Keychain caching uses the application bundle identifier as documented by `MSALCacheConfig.h`; cross-application token sharing is disabled. The app declares only its own `TEAM_ID.bundleIdentifier` access group in `IIVEPlayer.entitlements`. Xcode generated the matching Mac development provisioning profile using the existing Personal Team; the final signature includes that group and the application identifier. UserDefaults holds only the public client ID and selected account identifier. Tokens remain in the SDK cache. Background queue loading only attempts silent refresh; it never opens a login window unexpectedly.

**Disconnect** removes this app's selected account from the MSAL cache. It does not remotely revoke already issued URLs or sign out the system browser. Already-open streams can continue; later resolution requires sign-in again. Changing the configured client ID disconnects the currently selected account first. Multiple simultaneously selected accounts and sovereign-cloud endpoints are not implemented.

## Basic verification and outstanding checks

- Xcode Debug build with the real MSAL SDK passed; development apps are signed with the existing Personal Team and the matching private Keychain entitlement. On another development machine use Xcode automatic signing (or `xcodebuild -allowProvisioningUpdates`) to obtain its own matching profile. Development provisioning has a validity period; rebuild through Xcode if it expires.
- `bash scripts/check-onedrive.sh` passed URL-origin guards, HTTPS anonymous-content checks, pagination JSON parsing, duration-unit conversion and original filename/format handling. These are deterministic protocol tests, not a live Microsoft service test.
- `bash scripts/check-network-media.sh` passed the existing WebDAV/URL parsing checks.
- No GUI automation, interactive login, account-level token persistence, WAN throughput or full regression testing was performed. A registered client ID and your first login are still needed for end-to-end validation.

The preview currently covers the signed-in account's default drive and ordinary files. Shared shortcuts, cross-drive shared folders, search, offline downloads and seamless mid-stream URL renewal are not implemented. Unsupported files are disabled in the browser; absent metadata remains N/A. Metadata thumbnails are separate from seek-bar previews. Queue contents remain session-only.

The [Graph content API](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0) supplies expiring preauthenticated links; the implemented per-item refresh avoids queued links becoming stale before playback, but does not refresh an already open stream. Bounded position-preserving recovery and playback-aware metadata scheduling were subsequently implemented; see [delivery and recovery follow-up](delivery-network-recovery-20261021.md). These still need account/WAN validation. Shared-folder support remains future work.
